## Conformance notes

- **Standalone carrier (NOTEBOOK_SPEC 2.0 §4):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/smoldocling_document_extraction_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the default weights directory working-directory-relative), Section 3 carries the model identity and the 13-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the generating revision, the module's SHA-256, and the generator version.
- **Parity (PAR1–PAR3):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Model acquisition (MOD1–MOD8):** `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the manifest entries that are absent, from the Hugging Face Hub at the immutable revision (never `main`); `verify_snapshot` re-hashes every entry; `from_pretrained(weights_dir=WEIGHTS_DIR)` loads the verified files with `local_files_only=True` and `trust_remote_code=False` through `AutoModelForImageTextToText`/`AutoProcessor`. The processor, tokenizer and chat template come from the same snapshot; the upstream `onnx/` export is not listed and not used. The notebook's only external dependencies are the pinned PyPI distributions and the Hub at that revision.
- **Role stages:** `validate_inputs` writes `outputs/smoldocling_document_extraction_input_manifest.json` with the schema (supported instructions, token budget range, preprocessing, decoding rule), the ceilings, the input's observed mode and size, the request, the verdict, and one recorded rejection finding from the unsupported-instruction probe; `evaluation_report` writes `outputs/smoldocling_document_extraction_evaluation_report.json` — `sample-sanity` with one `word_error_rate` entry and one `element_count` entry per expected tag on the synthetic page; `not-measurable` on BYOD (with what labelled data would make the task measurable).
- The default sample is a deterministic 850×1100 report page rendered in code with Pillow's bundled font — the same page the smoke run used; `word_error_rate` against words you rendered yourself and element counts against structure you drew are sanity evidence for the input contract, forward pass, decoding and text recovery, not an OCR or layout metric. The page digest depends on the Pillow build's bundled font rendering and is printed, not asserted.
- Score semantics (UNC1–UNC4): generated markup carries no score, no probability and no correctness signal; the notebook says so before the first conversion and again in the interpretation section. The instruction and the token budget are caller-owned request parameters exposed as `# @param` values (defaults: the full-page instruction and `DEFAULT_MAX_NEW_TOKENS = 2048`) and passed explicitly on every `convert` call; `truncated` is surfaced and explained. The notebook performs no validation of its own — image, instruction and budget are checked only by the pipeline's `validate_inputs`/`convert` path.
- Ceilings `MIN_IMAGE_SIDE` (16), `MAX_IMAGE_SIDE` (4096), `MAX_NEW_TOKENS` (8192), `DEFAULT_MAX_NEW_TOKENS` (2048), `DECODING` and the seven `INSTRUCTIONS` are printed before the model runs.
- CPU is documented as adequate but slow (card-measured 6.3–21.8 s load depending on page cache, 21.1–21.7 s per 850×1100 page at 630 generated tokens); the notebook states that cost scales with the tokens generated and that GPU bfloat16 output need not match CPU float32 output token-for-token.
- `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
